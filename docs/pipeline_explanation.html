Updated Architecture Overview

ORCA Drowning Detection Pipeline

ORCA is a real-time drowning distress detection system built around pose-based temporal analysis. The repository originally came from a fall-detection structure, but the current objective is to detect drowning-related distress behavior in swimming pools using pose estimation, temporal modeling, decision logic, and structured alerts.

1. Project Context

The repository now contains two connected layers. The first is the real-time runtime pipeline used for webcam and video inference. The second is a formal machine learning development pipeline used for dataset building, training, evaluation, calibration, and model experimentation. The runtime path has been preserved while the development layer has been added around it in a modular way.

2. Runtime Pipeline

The runtime flow is:

Camera or video input -> YOLO pose detection -> multi-object tracking -> per-track buffering -> pose feature extraction -> TCN inference -> decision logic -> alert controller

Main runtime entry points:

  • scripts/run_yolo_cam.py for live webcam inference
  • scripts/run_yolo_track.py for video-file inference

3. Stage-by-Stage Runtime Explanation

Stage 1-2: Pose Detection and Tracking

Main files: pipeline/tracker.py, scripts/run_yolo_cam.py, scripts/run_yolo_track.py

YOLO pose tracking processes each frame, detects people, estimates body keypoints, and assigns stable IDs to each visible person. The output of these stages is a set of tracked observations containing bounding boxes, keypoints, confidence scores, and persistent track IDs.

Stage 3: Per-Track Buffering

Main file: pipeline/buffering/track_buffer.py

The buffering layer stores a rolling window of observations for each tracked person. This is necessary because drowning distress is a temporal behavior, not a single-frame event. Once enough history has been collected, the buffer emits a full sequence for downstream feature extraction.

Stage 4: Pose Feature Extraction

Main file: pipeline/featurization/pose_features.py

The feature extractor converts buffered pose history into a numerical tensor suitable for temporal inference. It normalizes pose relative to the person’s own body, includes geometry, confidence, velocity, and drowning-specific behavioral descriptors. The result is a time-ordered feature tensor X with shape (T, 50).

Stage 5: TCN Inference

Main files: pipeline/models/tcn.py, pipeline/models/inference.py

The Temporal Convolutional Network estimates the drowning-distress probability for each tracked person based on the Stage 4 feature sequence. Inference runs on a background worker in the runtime scripts so the main loop remains responsive. The inference path is implemented, but meaningful outputs still depend on trained drowning-specific weights.

Stage 6: Decision Logic

Main file: pipeline/decision.py

The decision layer turns noisy model probabilities into more stable behavioral states. It applies exponential moving average smoothing, hysteresis thresholds, hold-time requirements, cooldown logic, and stale-track cleanup. The output states are normal, possible, and confirmed.

Alert Controller

Main file: pipeline/alert_controller.py

Confirmed Stage 6 events are forwarded to the alert controller, which dispatches alerts asynchronously without blocking the runtime loop. It currently supports console logging, optional sound, optional webhooks, and leaves room for future GPIO, Arduino, or Jetson-style integrations.

4. Formal Development Pipeline

A formal machine learning development pipeline has been added so the repository can support structured experimentation without changing the real-time inference path.

  • dataset building from tracked sequences
  • training multiple model types such as TCN, LRCN, and TSM
  • evaluation on processed datasets
  • decision-threshold calibration
  • config-driven experimentation
  • preservation of older prototype code in legacy/

6. What the New Files Do

  • pipeline/utils/config.py loads YAML configuration files.
  • pipeline/models/registry.py provides model registration for configurable training.
  • pipeline/models/tcn.py defines the current primary temporal model used by the runtime inference path.
  • pipeline/models/lrcn.py defines the lightweight LRCN baseline model for feature-sequence training.
  • pipeline/models/tsm.py defines the lightweight TSM comparison model using temporal shifts over feature sequences.
  • pipeline/training/ contains dataset-building, dataloading, losses, metrics, and training logic.
  • pipeline/evaluation/ contains model evaluation and decision-calibration logic.
  • scripts/build_dataset.py builds processed samples from tracked video sequences.
  • scripts/train_model.py trains tcn, the baseline comparison lrcn, or the advanced comparison tsm models.
  • scripts/evaluate_model.py evaluates trained checkpoints.
  • scripts/calibrate_decision.py sweeps thresholds and produces updated decision settings.

7. Training And Evaluation Workflow

The intended development workflow is:

  1. collect labeled videos
  2. build processed feature-sequence samples with scripts/build_dataset.py
  3. train one model family at a time with scripts/train_model.py
  4. evaluate saved checkpoints with scripts/evaluate_model.py
  5. compare metrics across TCN, LRCN, and TSM

Example dataset building commands:

python scripts/build_dataset.py --video path/to/normal_video.mp4 --label 0
python scripts/build_dataset.py --video path/to/distress_video.mp4 --label 1

Example training commands:

python scripts/train_model.py --model tcn
python scripts/train_model.py --model lrcn
python scripts/train_model.py --model tsm

Example evaluation commands:

python scripts/evaluate_model.py --model tcn
python scripts/evaluate_model.py --model lrcn
python scripts/evaluate_model.py --model tsm

For a fair comparison, all three models should use the same processed dataset, the same labels, the same feature-vector version, the same split strategy, and the same evaluation metrics.

8. Current Status

The repository now supports both runtime inference and formal model-development work. The real-time drowning-distress pipeline remains preserved, while the surrounding tooling now supports dataset creation, model comparison, evaluation, and calibration. The main remaining work is experimental rather than structural: preparing drowning-specific datasets, training models, validating results, calibrating thresholds, and integrating trained weights back into the runtime path.
